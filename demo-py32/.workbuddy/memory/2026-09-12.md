# 2026-09-12

## 修复链接错误：region 'FLASH' already defined

**现象**：`cargo run` 链接阶段报 `rust-lld: error: memory.x:9: region 'FLASH' already defined`。

**根因**：`-Tlink.x` 被传了两次 ——
- `.cargo/config.toml` 的 `[target.thumbv7em-none-eabihf] rustflags = ["-C", "link-arg=-Tlink.x"]`
- `build.rs` 里 `println!("cargo:rustc-link-arg-bins=-Tlink.x")`

link.x 内部有 `INCLUDE memory.x`，重复解析导致 MEMORY 区域定义两遍。链接命令行中可见 `-Tlink.x --nmagic -Tlink.x -Tdefmt.x`。

**修复**：删除 build.rs 中的 `-Tlink.x` 一行，link.x 统一由 .cargo/config.toml 提供。`--nmagic` 与 `-Tdefmt.x` 保留在 build.rs（不冲突）。

**约定**：link.x 只在一处传递（选 .cargo/config.toml）；memory.x 靠 `INCLUDE` 在当前工作目录（crate 根）被找到，未做 OUT_DIR 拷贝 + link-search。

## 后续：-Tlink.x 两边都没了 → _start 警告（同上文件，当日收尾）

用户随后把 `.cargo/config.toml` 里的 `rustflags` 整段删掉（同时也把 runner 的 `--release` 挪到了末尾），而 build.rs 里的 `-Tlink.x` 已被我删过，结果**两处都没有**：

- 链接仍然“成功”，但 `warning: linker stderr: rust-lld: cannot find entry symbol _start` 出现；
- 实测产物 `entry = 0x00000000`，link.x 完全没加载，内存布局是 LLD 默认脚本（产物不可用）。

**最终落地（当前状态）**：三个链接参数统一放在 `build.rs`（`--nmagic` / `-Tlink.x` / `-Tdefmt.x`），`.cargo/config.toml` 不再有 rustflags；runner 去掉 `--release`（probe-rs 0.31.0 的 `run` 无此参数）。

**验证结果**：release 产物 `entry = 0x08000199`（= `Reset`），`__vector_table @ 0x08000000`，`__RESET_VECTOR @ 0x08000004`，无警告。

**排查手段**：PowerShell 工具不返回 stdout，必须 `2>&1 | Out-File -Encoding utf8 -Width 8192` 再读；可用极简 ELF 解析脚本直接查入口/向量表符号（已固化为技能 `cortex-m-link-troubleshoot`）。

## 后续 2：probe-rs 报 "Failed to parse defmt data / no version symbol"

现象：链接通过、`cargo run --release` 进入 probe-rs 后报
`1: `.defmt` section found, but no version symbol - check your linker configuration`。

根因：`-Tdefmt.x` 生效，但 `main.rs` 里**没有任何 defmt 日志调用**。
- `defmt.x` 会无条件生成 `.defmt` 段（实测产物里该段长度 1、地址 0），probe-rs 见到就尝试解码；
- defmt 的版本标记是 `defmt` crate 根 `lib.rs` 里的 `#[used] #[link_section=".defmt.end"] #[export_name = "_defmt_version_ = 4"]` 静态量，只有 defmt 被真正引用时才会进符号表（实测 173 个符号里 0 个 defmt 符号）；
- 依赖关系：`defmt "0.3"` → `defmt 0.3.100`（转接壳）→ 真正的 `defmt 1.1.1`；`defmt-rtt 0.4.2` 也走这个壳，因此并不存在双版本冲突。

处置（用户选择「移除未使用的 defmt 依赖」）：
- `Cargo.toml` 删掉 `defmt = "0.3"`、`defmt-rtt = "0.4"`（Cargo.lock 中 defmt 已全部消失）；
- `build.rs` 去掉 `-Tdefmt.x`，只留 `--nmagic` + `-Tlink.x`；
- 输出继续只走 UART2。

**验证**：release 无警告；`entry = 0x08000199`（= `Reset`）、`__vector_table @ 0x08000000`；产物中 `.defmt` 段已消失。

**约定**：`-Tdefmt.x` 只在工程真的会打 defmt 日志时才加；否则 probe-rs 会因缺版本符号拒绝烧录。

## 后续 3：按需求重新启用 defmt-rtt（最小可用）

用户改主意："还是启用一丢丢 defmt-rtt，不然不知道有没有正常运行"。最终配置：

- `Cargo.toml`：恢复 `defmt = "0.3"` + `defmt-rtt = "0.4"`（0.3.100 是转接壳，真实实现 defmt 1.1.1）；
- `build.rs`：恢复 `-Tdefmt.x`（注释里写清"用 defmt 才传"，三种坑都记了）；
- `src/main.rs`：加 `use defmt_rtt as _;`（全局 logger），init 之后一条
  `defmt::info!("boot ok, hclk={} Hz", clocks.hclk.0)`；panic handler 改成
  `defmt::error!("PANIC: {}", defmt::Display2Format(info))` 再挂死（原先静默卡死看不出是没跑还是 panic）；
- `.cargo/config.toml`：新增 `[env] DEFMT_LOG = "info"`。

**关键知识点（踩到了）**：defmt 的等级过滤是**编译期**的。`DEFMT_LOG` 未设置时默认等级是 `error`
（`defmt-macros/src/function_like/log/env_filter.rs`：`LEVEL_WHEN_NOTHING_IS_SPECIFIED = Some(Level::Error)`），
所以第一次编出来 `.defmt` 段里只有 `PANIC: {}`，`info!` 被整体剔除（连字符串都没有）。加上 `DEFMT_LOG="info"` 后正常。

**验证**（release，无警告）：`.defmt` 段 7 字节；符号表里同时有 `_defmt_version_ = 4`、
`_defmt_encoding_ = rzcobs`、`_defmt_acquire/_release/_write`、defmt-rtt `BUFFER`(1024B, RAM)、
以及 `boot ok, hclk={} Hz`（defmt_info）与 `PANIC: {}`（defmt_error）；`entry = 0x08000199`（= `Reset`）不变。

**约定**：新增 defmt 日志时记得 `DEFMT_LOG` 调级（level 不够高会被编译掉，容易误以为"没跑起来"）。

## 后续 4：实机跑通 —— 真正的拦路虎是芯片描述 YAML 缺 RAM 段

用户要求"你自己跑一遍"。实际执行 `cargo run --release` 后发现：**烧写成功，但 probe-rs 一条 RTT 日志都不打，进程静默挂着**。

排查路径（关键是让 probe-rs 自己吐内部日志，用 `--log-file`）：

```
probe-rs run --chip-description-path PY32E4_Series.yaml --chip PY32E407xE --log-file probe.log <elf>
```

`probe.log` 里的真凶：

```
Failed to attach - control block corrupted: the write buffer doesn't fully fit in any known
(consecutive) ram region according to its own pointers: (start_pointer: 0x20000058, size: 1024)
```

**根因**：`PY32E4_Series.yaml`（`generated_from_pack: true`，自动生成）里 PY32E407xE 的 `memory_map`
**只保留了最后一段 CCM_SRAM**（0x2001c000..0x20024000），SRAM1/SRAM2 全丢了。
而本工程 `.data/.bss` 在 0x20000000 段（defmt-rtt 的 RTT 缓冲区在 0x20000058），不属于任何已知 RAM，
probe-rs 拒绝附着 RTT —— 所以"没报错但也没日志"。

用 `Puya.PY32E4xx_DFP.1.0.0.pack` 里的 `.pdsc` 核对，官方为四段：

| 区域 | 地址 | 大小 |
|---|---|---|
| Flash | 0x08000000 | 0x80000（512K） |
| SRAM1 | 0x20000000 | 0x18000（96K） |
| SRAM2 | 0x20018000 | 0x4000（16K） |
| CCM_SRAM | 0x2001c000 | 0x8000（32K） |

SRAM1+SRAM2 = 0x20000000..0x2001c000 = 112K，与 `memory.x` 的 `RAM : ORIGIN = 0x20000000, LENGTH = 112K` 完全吻合。

**修复**：已在 YAML 的 PY32E407xE 变体里补上 SRAM1 / SRAM2 / CCM_SRAM 三段 `!Ram`。

**验证（同一命令重跑）**：probe.log 出现 `Attached to RTT`，控制台打印

```
[INFO ] boot ok, hclk=80000000 Hz (demo_py32 demo-py32/src/main.rs:79)
```

即 HCLK = 80 MHz，与 `enable80mhz()` 的期望一致，程序确实在跑。

**遗留**：`PY32E407xC` / `PY32E407xD` 两个变体有同样的缺陷（也只剩 CCM_SRAM），当前未改。
另外 YAML 是自动生成的，重新生成会覆盖本次修正，需要同步修生成脚本。

**顺带记录**：RTT 首次扫描会先失败（目标刚复位、控制块未初始化），probe-rs 清空控制块后重试即成功，属正常。

## 后续 5：PB1/PB2 每 100ms 翻转（去掉 PA5）

用户要求：控制 PB1/PB2 不停翻转；确认后选择"关闭 PA5 / 保留 UART2 回显 / 用 100ms 延时"。

`src/main.rs` 改动（结构未动，只替换 GPIO 部分）：
- 顶部用法示例 `p.PA5` → `p.PB1`；
- `let mut led = Output::new(p.PA5, ...)` → `pb1` / `pb2` 两路 `Output::new(p.PBx, Level::Low, Speed::Low)`；
- 主循环里 `led.toggle(); delay_ms(500)` → `pb1.toggle(); pb2.toggle(); delay_ms(100)`；
- 用户在循环里自己加的 `defmt::info!("Ciallo")` 保持不动。

**实测（真机）**：
1. RTT 正常，`Ciallo` 持续输出 → 程序在跑；
2. 采样 GPIOB_ODR（`probe-rs read b32 0x48000414 1`）得到 `0x00000000` / `0x00000006` 交替
   → PB1(bit1)+PB2(bit2) 确实同相翻转，验证通过（也证明结束 probe-rs 会话后目标继续运行）；
3. 用日志行数反推主循环频率：**4.00 Hz，翻转间隔约 250ms**，而不是代码里的 100ms。
   原因是循环里那次阻塞式 `uart.read()`：`uart.rs` 的 `TIMEOUT_LOOPS = 1_000_000` 是**忙等自旋计数**而非真实时间，
   无数据时约耗时 150ms，于是 100ms + 150ms ≈ 250ms。
   若要做到精确 100ms，需去掉/降低 UART 轮询频率（例如每 N 次循环才读一次 UART）。
4. 脱离调试器 30 秒后再采样，仍在翻转 → 循环里的 defmt 日志在无主机读 RTT 时**不会**卡住主循环
   （日志应在缓冲区满后被丢弃），单独上电运行是安全的。
