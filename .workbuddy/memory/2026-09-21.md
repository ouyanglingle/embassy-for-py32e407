## 评估：cbind-rs 是否该改（用户提出「main 里还要用寄存器和 unsafe」）

### 调研事实（供后续决策用，避免重复查）
- **LL 头里 `__STATIC_INLINE` 总数 ≈ 2068**（按 `Inc/py32e407_ll_*.h` 计数）：
  TIM 276、USART 200、DMA 167、LPUART 160、ADC 150、RCC 127、I2C 125、SPI 109、
  FLASH 82、LPTIM 76、SYSTEM 67、UART 63、PWR 54、RTC 43、CTC 43、DAC 40、
  LCDC 37、COMP 35、OPA 30、CORDIC 28、bus 25、cortex 25、**GPIO 23**、EXTI 22、
  CRC 20、RNG 13、WWDG 12、IWDG 11、utils 5。
- **bindgen 0.71.1 的 `wrap_static_fns` 可用**（docs.rs 确认）：公开方法
  `wrap_static_fns(bool)` / `wrap_static_fns_path(path)` / `wrap_static_fns_suffix(suffix)`，
  **文档里没有 feature 门控**（对比 `vtable_generation` 明确标 experimental）。
  行为：生成一个 C 源文件（内含非 static 包装函数，默认后缀 **`__extern`**），
  **需要自己用 cc 编译它**才能从 Rust 调用。
- LL GPIO 头的 23 个 inline 函数清单已确认（SetPinMode/GetPinMode/SetPinOutputType/
  SetPinSpeed/SetPinPull/SetAFPin_0_7/8_15/LockPin/ReadInputPort/IsInputPinSet/
  WriteOutputPort/ReadOutputPort/IsOutputPinSet/**SetOutputPin/ResetOutputPin/TogglePin** …）。

### 判断（待用户定 scope）
1. **「还要用寄存器（PAC）」= cbind-rs 的真实缺陷，值得修。** 两法：
   A. `wrap_static_fns` 全量自动包装（2000+ 个，一劳永逸，跟头文件自动同步；
      风险：生成物巨大、编译时间涨、个别函数可能包装失败导致整体 build 挂）；
   B. 手写 `shim.c` 精选（GPIO/bus/utils 里挑 20~30 个；零风险、可控，
      与该 crate 现在"精选 + 排除 HAL 依赖"的风格一致；代价是加外设要手动补）。
   **倾向 B**，覆盖面大起来再切 A。
2. **「unsafe」不是 cbind-rs 少做了什么，而是 FFI 路线的固有成本。**
   任何 `extern "C"` 调用都必须 `unsafe`；把 2068 个函数全包装出来，调用方照样要写 unsafe。
   要让调用方不写 unsafe，只能在 cbind-rs 里**再叠一层安全包装**（就像它已给
   `LlRccClocks::read()` 做的那样）。⚠️ 但把安全层做全 ≈ 重写一遍 **embassy-py32**——
   项目里已经有一个完整的安全 Rust HAL 了。

### 因此需先定 cbind-rs 的定位
- 定位 A「薄 FFI 逃生舱」（给 embassy-py32 没覆盖的外设 / 对照官方 C 行为）→ 只修 1，
  unsafe 保持原样（这是该路线的性质，不是缺陷）。
- 定位 B「可独立使用的库」→ 1+2 都做，但要接受与 embassy-py32 大量重叠，或考虑合并。

已就此向用户提 scope 选择，等回复后再动 `py32e407cbind-rs`。

### 关键纠正（旧认知是错的）
**bindgen 并不会为 `__STATIC_INLINE` 生成声明**（实测 bindings.rs 里 `LL_GPIO_TogglePin` /
`LL_AHB2_GRP1_EnableClock` **零匹配**）。原因是 `static` 是内部链接，只在每个用到它的 `.c` 里
内联、最多留局部符号（`nm` 小写 `t`），bindgen 根本不把它当可绑定函数。所以：
- 别名不会撞名（那些名字本来就是空的）；
- **不需要** bindgen 的 `wrap_static_fns` 也能做 shim。

### 删掉 PAC 后必踩的一步
`undefined symbol: _critical_section_1_0_acquire/_release`。`cortex-m` 的
`critical-section-single-core` feature 提供这两个符号，但**没有任何代码引用 `cortex-m`**
时链接器不会把它拉进来（以前是 PAC 在引用它，所以看不出来）。修法：main.rs 里写
**`use cortex_m as _;`**（与 `use defmt_rtt as _;` 同理）。

### 验证
- `arm-none-eabi-nm --defined-only <out>/libpy32e407_ll.a | findstr __ext` → **52 个全部全局 `T`**
- `cbind-demo cargo build --release` → **Finished，0 error 0 warning**
- `arm-none-eabi-objdump -f` → `start address 0x08000401`（Flash，link.x 生效）
- `arm-none-eabi-size` → text **6488 → 7240**（+752 B；因 build.rs 有 `-ffunction-sections`
  + 链接 `--gc-sections`，**只有实际用到的 7 个 `__ext` 进了最终镜像**，nm 已确认就那 7 个）
- **未上板**（未接 probe），行为正确性仍只有链接/布局层面证据

### 技能维护
`py32e407-cbind-ffi` 已更新：description、分工表（不再需要 PAC）、新增「三层结构与 shim」节
+「增补一个函数的步骤」、纠正 bindgen 不生成 inline 声明这一条、工程骨架去掉 PAC 并加
`use cortex_m as _;` 警示、启动流程表全部换成 LL/shim 写法。
`references/pattern-map.md` 重写为 **「shim 优先，PAC 后备」**（A 段全 shim 可复制代码，
B 段保留 PAC 等价表供未覆盖外设用，C 段常量表补 `GPIO[A-F]_BASE` 与 `LL_PWR_*`）。

### 待办
- 其余外设的 inline（RCC 选时钟源、USART/TIM/SPI 收发与使能）**仍未纳入 shim**——
  也就是说目前用 cbind-rs 还**做不了完整串口收发**，要用得先按步骤补 shim。
- 若覆盖面继续膨胀，再评估切到 bindgen `wrap_static_fns` 全量自动包装
  （bindgen 0.71.1 已有 `wrap_static_fns` / `_path` / `_suffix`，默认后缀 `__extern`，
  docs 里没有 feature 门控）。

## 第二轮：用户指出「一个个加不现实」→ 改成全量自动导出（同日，已落地）

### 触发
用户："那我要是要用 GPIOB 呢 / USART2 呢？这类东西你要给我全部导出啊"。
（先澄清：**GPIOB 本来就能用** —— 外部化是按 **API** 而不是按外设实例，
`LL_GPIO_*` 收的是 `GPIO_TypeDef*`，任何端口都行；`GPIO[A-F]_BASE` 也已导出。
另外 **PY32E407 没有 HUART 外设**，用户说的应是 UART2/USART2。）

### 交付物
- **删掉** `csrc/ll_shim.h` + `csrc/ll_shim.c`（52 个手写精选）+ 整个 `csrc/` 目录。
- `build.rs` 改为 bindgen 的 **`wrap_static_fns(true)`** +
  `wrap_static_fns_path(OUT_DIR/ll_static_fns_ext)` + `wrap_static_fns_suffix("__ext")`：
  bindgen 自动生成 `ll_static_fns_ext.{h,c}`，再由**第二个 `cc::Build`**
  （必须在 bindgen 之后）编成 **`libpy32e407_ll_ext.a`**。
- allowlist 从 `GPIO[A-F]_BASE` 放宽为 **`.*_BASE`**（`USART2_BASE` / `UART2_BASE` /
  `LPUART_BASE` / `I2C3_BASE` / `TIM1_BASE` / `SPI3_BASE` … 全可用）。
- `src/lib.rs`：去掉手写的 `gpio_ext`/`bus_ext`/`pwr_ext` 别名模块；
  也**不需要** alias 生成（见下）。

### 最关键的一条认知（推翻了我上一轮的假设）
**bindgen 为包装生成的 Rust 名就是官方名**，靠 `#[link_name]` 重定向：
```rust
#[link_name = "LL_USART_TransmitData8__ext"]
pub fn LL_USART_TransmitData8(USARTx: *mut USART_TypeDef, Value: u8);
```
所以 **`pub fn \w+__ext` 在 bindings.rs 里零匹配**，`__ext` 只出现在属性里。
⇒ 我为"把 `__ext` 名字别名回官方名"写的 `write_ext_aliases()`（扫 bindings.rs 生成
`pub use`）**是多余的**，它跑出空文件——已删除该函数与对应 `include!`。
教训：**先看 bindgen 实际生成了什么，再写后续处理**；我按"bindgen 只会给带后缀的名字"
推测就动手，白做了一轮。

### 验证
- `nm --defined-only libpy32e407_ll_ext.a | findstr " T " | find /c /v ""` → **2058**
- 抽查确认可用：`LL_GPIO_TogglePin` / `LL_AHB2_GRP1_EnableClock` / `LL_USART_Enable` /
  `LL_USART_TransmitData8` / `LL_USART_ReceiveData8` / `LL_USART_IsActiveFlag_TXE` /
  `LL_LPUART_Enable` / `LL_RCC_ConfigMCO`（USART 一个头就有 200 个 inline，手写确实不现实）
- bindings.rs 抽查：`pub fn LL_USART_TransmitData8(USARTx: *mut USART_TypeDef, Value: u8);` ✓、
  `pub const USART2_BASE` / `UART2_BASE` / `LPUART_BASE` / `GPIOB_BASE` ✓
- `cbind-demo cargo build --release` → **Finished，0 error 0 warning**；
  `size` text 仍是 **7240**、`objdump -f` 入口 **0x08000401**（在 Flash）
  —— 说明 `-ffunction-sections` + `--gc-sections` 把没用到的 2051 个包装全裁掉了，
  **全量导出几乎不占固件**（相比只导出 52 个时的 7240 完全相同）。
- 构建耗时：bindgen 全量 + 编译 2058 个包装约 25~35 s（可接受）。

### 结论/待办
现在**任何外设的 inline 函数都可用**，包括完整串口收发。唯一例外是 **USB / SDMMC**
（LL 头依赖 HAL 层，本 crate 本就排除）。加新外设**什么都不用做**。

## 第四轮：新建 py32e407hal-rs（HAL 绑定 + hal-demo）

### 触发
用户："再新建一个文件夹，专门用来把所有的 HAL 库导出来，同时再新建个 hal 库示例"。

### 设计选择（重要偏差记录）
- **不走 bindgen**：HAL 头层层嵌套（master `py32e4xx_hal.h` → `py32e407_hal_conf.h` → 各模块头
  → `py32e407_hal_def.h` → 设备头），加上宏开关选模块，bindgen/libclang 反复调 include 顺序
  都失败（实测 `error: unknown type name 'HAL_StatusTypeDef'` 即使 `#include "py32e407_hal_def.h"` 也在前）。
  **改用 Rust 侧手写 extern 声明**：HAL 函数总共约 200 个，分组列在 `src/lib.rs` 里，按官方头
  原型照抄。HAL 函数大都在 `.c` 里（不像 LL 全是 static inline），手写可行。
- **Handle 必须按 C 布局暴露字段**：`UART_HandleTypeDef` / `DMA_HandleTypeDef` 不能 opaque —
  HAL 内部按字段偏移读写（`huart->gState = ...`、`huart->hdmatx->XferCpltCallback = ...`），
  Rust 侧字段顺序与 C 严格一致（`#[repr(C)]`），并加尾缓冲 `_trail: [u8; N]` 防越界。
- **HAL 必须配 cbind-rs**：HAL 的 .c 引用了 `LL_*` 符号（HAL 是 LL 之上的状态机封装），
  hal-rs 的 Cargo.toml 直接把 `py32e407cbind-rs = { path = "..." }` 列为依赖，
  用户用时同理必须两个 crate 同时加。
- **HAL 中断状态机被绕过**：HAL 的状态机靠 DMA/UART ISR 推进；本工程没有 NVIC 向量表，
  ISR 不会触发 → 例子用 **LL 轮询 DMA TC 标志**判断完成，再把 `huart.gState` 手动复位。
- **`HAL_GetTick` / `HAL_Delay` 必须由本 crate 提供**：HAL 弱默认是空（`__weak`），
  hal-rs 提供 Rust 强符号实现（`HAL_TICK_COUNT` + `bump_tick()`），用户主循环 1ms 节拍里调一次。

### 交付物
- **`py32e407hal-rs/`**：`Cargo.toml` / `build.rs` / `csrc/py32e407_hal_conf.h` / `src/lib.rs` /
  `src/hal_consts.rs`（空壳）+ `.cargo/config.toml`（runner 引用 `demo-py32/PY32E4_Series.yaml`）。
- **`hal-demo/`**：与 `cbind-demo` 同结构（5 个文件），但用 HAL API。
  移植依据：官方 HAL 例程
  `参考设计/.../Projects/PY32E407-STK/Example/UART/UART_HyperTerminal_DMA/Src/main.c`。

### HAL 调试踩到的坑
1. **没有 `py32e407_hal_conf.h`** → `py32e4xx_hal.h` 第一个 `#include "py32e407_hal_conf.h"` 找不到。
   解决：本 crate 自带一份精简 conf（`csrc/`），cc 与 bindgen 都要把 csrc 加到 include 路径。
2. **conf 不要 include 主头**：HAL 主头自己会 include conf，反向 include 会循环；最后把
   `assert_param` 宏也显式定义（USE_FULL_ASSERT=0 时也要有 `((void)0U)` 兜底），
   否则 `.c` 里调 `assert_param(...)` 报 implicit declaration。
3. **`py32e4xx_hal.h` 自己不拉设备头**：它假定 conf.h 已经拉过；所以 conf.h 必须按 enable 列表
   include 各个 `py32e407_hal_*.h`，让模块头拉入 `py32e407_hal_def.h`（→ 设备头）。
4. **bindgen 链路失败**：HAL 头顺序敏感，bindgen/libclang 调不下来 → 改手写 Rust 声明。
5. **`DMA_HandleTypeDef.pParent` 是 `void*`**：HAL 用它反向找回 UART/SPI/I2C 句柄
   （指向 `UART_HandleTypeDef*`），Rust 侧用 `*mut core::ffi::c_void`。
6. **status enum 的 `Format` trait**：`HAL_StatusTypeDef`/`HAL_UART_StateTypeDef` 是 Rust enum，
   `{:?}` 会触发 Debug，要求派生 `Debug` —— 否则 defmt 输出用 `{}` + 强转 u32 更稳。

### 验证
- `py32e407hal-rs cargo build --release` → **Finished, 0 error**
- `hal-demo cargo build --release` → **Finished, 0 error**
- `hal-demo` 最终镜像：`text=11824 / data=60 / bss=1036`；入口 `0x08000401` 在 Flash
- `nm` 确认链接：`HAL_UART_Init`、`HAL_UART_Transmit_DMA`、`HAL_DMA_Init` 在 `0x0800xxxx`；
  `LL_*__ext`（外部化的 LL inline）也在；`SystemCoreClock` 在 `0x20000000`(.data)
- ⚠️ **仍未上板**（未接 probe）。HAL 与 LL 混用的一个**已知风险**：HAL 函数按官方
  字段偏移读写 handle，Rust 侧必须严格匹配 `_trail` 字节数；目前是按官方头手算的，
  上板后若有 DMA/UART 异常第一时间检查 `DMA_HandleTypeDef` 大小与
  `UART_HandleTypeDef` 是否与官方 `__alignof__` 对齐（可能需要把 `Instance`/`Init`
  字段加 `#[repr(C, align(N))]` 重新对齐 —— 当前没用，但写进了"待上板排查"清单）。

### 技能维护（本轮已做）
- `py32e407-cbind-ffi` 技能 description 提及「对偶的 HAL 库 py32e407hal-rs」。
- 新增「HAL vs LL 路线选择」段（何时选 HAL、何时选 LL、HAL 中断状态机依赖、
  `_trail` 字节对齐风险）。

### 下一步
- 上板验证 hal-demo（DMA TC 标志轮询是否真的触发、波特率是否对）。
- 若 hal-rs 后续要扩到 SPI/I2C/TIM 等：按 `src/lib.rs` 现有格式追加 extern 声明（模板现成），
  并在 `py32e407_hal_conf.h` 取消对应模块的注释。

### 触发

### 移植依据（权威，别自创）
`参考设计/PY32E407_Firmware_V0.7.0/Projects/PY32E407-STK/Example_LL/UART/UART_HyperTerminal_DMA/Src/main.c`
—— 通道号、请求号映射、引脚/AF 全部照抄。

### 硬件/资源分配（本项目从此固定）
| 信号 | 引脚 | 说明 |
|---|---|---|
| LED/方波 | **PC3** | 推挽输出，1 ms 翻转 → 500 Hz |
| UART2_TX | **PC12** | AF5，推挽+上拉（官方 STK 同款） |
| UART2_RX | **PD2** | AF5 |
| UART2_TX DMA | `DMA1` **CH1** | 请求号 1，方向 M2P，目的端 HARD 握手 |
| UART2_RX DMA | `DMA1` **CH2** | 请求号 2，方向 P2M，源端 HARD 握手 |
串口 115200 8N1。RX 用**定长块**（16 B，收满才处理、才回显），与官方例程同模型。

### 第三轮发现（重要，属新认知）
**① 第二类坑：常量也会被 bindgen 静默丢弃。**
函数之外，**带 `((uint32_t)…位宏)` 强制转换的宏整条被丢掉**（不报错、不留痕）。
实测规律极干净：同组里纯字面量的在，带转换的全没。受影响例子：
`LL_DMA_DIRECTION_MEMORY_TO_PERIPH` / `LL_DMA_SRC_ADDR_FIX` / `LL_DMA_PRIORITY_1..5` /
`LL_DMA_*_PERIPH_MAP_2..6` / `LL_UART_DATAWIDTH_8B` 等。

**② 修法要两层，缺一层都不行**：
- 第一层（必须先在 build.rs 做）：allowlist 加 **`[A-Z][A-Z0-9_]*`**，
  把设备头的寄存器位宏（`DMA_CH_CTRLL_TT_0`、`UART_CR1_M_0`…）纳入常量表 ——
  bindgen 求值宏时**只在自己已生成的常量表里查标识符**，查不到就丢整条。
  （我一开始以为「宏是宏引用宏的三层结构」是唯一原因，加了这条后
  `DMA_CH_CTRLL_TT_0` 确实出现了，但依赖它的 LL 常量**还是没出现** →
  说明还有第二层原因。）
- 第二层：**试过加 `u?int(8|16|32|64)_t` 到 allowlist 修不好**（已实测，别再试）。
  只能在 Rust 侧补：**新增 `py32e407cbind-rs/src/ll_consts.rs`**。
  ⚠️ 它是**子模块**，绑定在 crate 根 ⇒ 文件顶部必须 `use crate::*;`。
  ⚠️ 补的时候**不写魔数**：第一层做完后位宏已在 Rust 侧，直接逐字转写官方 `#define`：
  `pub const LL_DMA_DIRECTION_MEMORY_TO_PERIPH: u32 = DMA_CH_CTRLL_TT_0;`

**③ build.rs 新增对账检查（缺口可视化）**：扫 LL 头里所有对象式 `LL_*` 宏与 bindings.rs 对账，
有缺失就 `cargo:warning` 报数量+样例。**基线 199 个**，绝大多数是
`LL_ADC_AWD_CHANNEL_*` / `LL_CORDIC_*` / `LL_COMP_*`（本项目不用）。
DMA 与 UART 两组已由 `ll_consts.rs` **全部补齐**。

**④ PY32 DMA 与 STM32F4 结构完全不同**：是「通道 → 请求号 → 外设」两段式映射
（近似 STM32L4/G0 的 DMAMUX）。每条通道必须**成对**配：
`LL_DMA_SetDstPeriphMap(DMA1, CH1, ..._MAP_1)` **且**
`LL_SYSCFG_SetDMARemap(DMA1, ..._MAP_1, LL_SYSCFG_DMA_MAP_UART2_TX)`。
⚠️ 后者写 `SYSCFG->CFGR`，**必须先开 SYSCFG 时钟**（`LL_APB2_GRP1_EnableClock(PERIPH_SYSCFG)`），
否则静默失效（现象：通道/请求都开了但一个字节都不动）。

**⑤ `UART` 与 `USART` 是两套独立外设**：`UART_TypeDef.DR` 在**偏移 0x00**、
`USART_TypeDef.DR` 在 **0x04**。DMA 的 `SetDstAddress` 写错偏移 → 数据搬到 `BRR` 上，
现象是波特率全乱。官方 STK 例程用的是 **UART2**（`LL_UART_*` 函数族）。
另外 **PY32 的 UART 没有使能位**（LL 里没有 `LL_UART_Enable`），时钟开 + `LL_UART_Init` 即可工作。

### 设计决策（写在代码注释里了）
- **用轮询代替中断**：官方例程用 `NVIC_EnableIRQ(DMA1_Channel1_IRQn)`，但中断向量表的中断项
  来自 linker `device.x` 的 `__INTERRUPTS`，那是 PAC（`rt` feature）才有的东西；
  本工程已不依赖 PAC ⇒ **没有向量表**。别为一个 demo 造向量表，改主循环轮询完成标志。
  仍调 `LL_DMA_EnableIT_TFR` 但**不碰 NVIC**（保证 `STATUSTFR` 可靠置位）。
- **`TxState` 软件记账 + 超时兜底**：两个硬件行为手册没写死，不敢依赖 ——
  `CH_EN` 传输完是否自动清零、`STATUSTFR` 在中断屏蔽时是否仍置位。
  超时 100 ms（16 B @115200 ≈ 1.4 ms）。**没有它的话请求映射写错会让发送路径静默永久卡死**，
  现场完全看不出问题。
- **DMA 缓冲放 `main` 的栈上**（`main` 是 `-> !`，栈帧永不返回 → 地址天然稳定），
  不用 `static mut`；但**正在被 DMA 读的缓冲绝不能改写** ⇒ 回显缓冲单独一块，
  且只在 TX 空闲时才 `copy_from_slice`，否则丢弃本块并 `defmt::warn`。
