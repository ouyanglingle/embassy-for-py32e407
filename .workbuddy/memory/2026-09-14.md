### ★ 真正的根因（定位完成，2026-09-14 下午）
- **`rcc.rs` 从未配置 `PWR_CR1.VOS`（VDDD 内部 LDO 电压档）—— 这是跑高频的前提。**
  官方 C 在启动代码 `demo/Core/SRC/system_py32e407.c::SystemInit()` 里明确做了：
  `SET_BIT(RCC->APB1ENR1, PWREN)` → `CLEAR_BIT(PWR->CR1, PWR_CR1_VOS)` → `CLEAR_BIT(PWR->CR1, PWR_CR1_SRAM_RETV)`。
  `PWR_CR1` 属备份域、**系统复位不清零** → Rust 侧继承低压档 → 高频上不去。
- 这一条解释了**此前全部现象**：≤80MHz 能跑（A 的 56MHz、扫描 ≤24MHz ✓），>80MHz 全失败（168MHz 各组 ✗），
  而 C（`demo`，Low 档 ÷8×168 = 168MHz）正常 ✓ —— 与晶振频率、驱动档、PLL 分频**都无关**。
  → **用户坚持的"YXC 8MHz 无源晶振"完全正确；我此前的"24MHz"结论彻底作废并已收回。**
- **修复**：`embassy-py32/src/rcc.rs` 新增 `set_pwr_high_voltage()`（使能 `APB1ENR1.PWREN` → `VOS=00`、`SRAM_RETV=00`），
  在 `init()` 最开头（step 0）调用。字段位置：`PWR_CR1.VOS` bit[10:9]、`SRAM_RETV` bit[12:11]；PAO `pac::Pwr = Periph<pwr::RegisterBlock, 0x4000_7000>`。
- demo 时钟配置恢复为 studio `demo` 的精确参数（`HseDrive::Low` / `PLL DIV8×168` / `sys=PLL` / `freq=8MHz`），
  成功时应打印 `clocks: sys=168000000`。release 0 error 0 warning。
- **教训（重要）**：PY32 启动代码 / `HAL_MspInit` 里做的事驱动不能想当然跳过，尤其是**与最高频率相关的 LDO 电压档 (VOS) 与备份域寄存器**（系统复位不清）。

### 关于"clocks() 显示的频率是不是真的"
- **不是测量值**。`rcc.rs` 的 `clocks()` 返回的是 `init()` 里用「`hse.freq`(调用方填的字段) × mul ÷ prediv ÷ postdiv」算出来、存进原子的值。
- **embassy-stm32 也一样**（已查源码，`参考设计/embassy-stm32-0.6.0/src/rcc/`）：
  `mod.rs` 里 `static CLOCK_FREQS: MaybeUninit<Clocks>`，`clocks()` = `unsafe { get_freqs() }` 直接返回缓存的全局；
  `init` 中的 `.read()` 全是就绪标志等待（`hsirdy/hserdy/pllrdy/sws`），**没有频率测量**。
  → 它显示的数字同样是"按配置 + HSE_VALUE 常量算出来的纸面值"。
- 两者唯一实质差别：embassy-stm32 的 `HSE_VALUE`/`HSI_VALUE` 是**编译期常量**（build config），
  而本驱动的 `Hse.freq` 是**运行期结构体字段**，填错了就会"自信地报错频率"——这正是这轮踩的坑。
- 要拿真值只有两条路：(1) 读寄存器反推（反映硬件实际配置，但仍假设晶振值）；(2) 实测引脚/引 MCO。
