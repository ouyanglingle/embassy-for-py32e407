- 规则：同步（Blocking）驱动的构造函数一律 `new_blocking` / `new_blocking_with_*`，
  **`new` 留给后续的 Async 版本**。与 embassy-stm32 0.6.0 的 `Uart::new_blocking` /

- 本次改动：
  - `lpuart.rs`：`Lpuart::new`→`new_blocking`、`new_with_tx`→`new_blocking_with_tx`、
    `new_with_rx`→`new_blocking_with_rx`、`LpuartTx::new`/`LpuartRx::new`→`new_blocking`，
    并修正全部 doc 内链（此前模块文档已写 new_blocking 但函数没改，链接是断的）。
  - `demo-py32/src/main.rs`：模块 doc 与两处调用点改为 `Uart::new_blocking` /
    `Lpuart::new_blocking`。
- 编译：embassy-py32 `cargo check --all-targets`、demo `cargo build` 均 0 error 0 warning。
- 技能 `references/style-guide.md` 的 API 命名一条已改写为上述约定（原来写的是"new 即可、

- 备注：embassy-stm32 0.6.0 的 `Uart` 组合类型上没有 tx/rx 半部构造器别名，只有

  - 仅 TIM2 是 32 位计数器（TIM3/4/5/18 共用 tim2 块但仍 16 位）；

  - 定时器内核时钟 x1/x2 规则成立：APB 分频≠1 时 TIMCLK=2×PCLK（官方例程
    TIM1_TimeBase_Init 的 PSC 算法为硬证据）。

  W::bits 位宽跨块不一致（tim2 PSC/ARR u32，tim9 RCR u16，tim15/16 RCR u32）。

## 新建 py32e407cbind-rs：C LL 驱动 FFI 封装（2026-09-13 晚）

- 需求：把 PUYA 官方 C LL 驱动编译为 Rust 可调用库，新建 crate `py32e407cbind-rs`（工作区根，与 embassy-py32/py32e407-pac 同级）。
- 做法：build.rs 用 cc crate 交叉编译 Drivers/PY32E407_HAL_Driver/Src/ 下的 py32e407_ll_rcc.c + py32e407_ll_gpio.c（只读引用、不复制官方固件，路径 ../参考设计/PY32E407_Firmware_V0.7.0/Drivers/...），产出 libpy32e407_ll.a；src/lib.rs 用 extern "C" + #[repr(C)] 复刻结构体（LL_RCC_ClocksTypeDef=4×u32、LL_GPIO_InitTypeDef=6×u32）暴露 RCC/GPIO 的 public 非 inline 函数。
- 已踩平的坑（关键）：
  1. build script 永远在 host 运行，cc 默认按 host 加 -m64，arm-none-eabi-gcc 不认 → 报错。必须在 build.rs 显式 .target("thumbv7em-none-eabihf") 覆盖。
  2. 必须定义 PY32E407xE（触发外设定义）+ USE_FULL_LL_DRIVER（否则 LL 的 .c 整文件被 #ifdef 吃掉、无任何符号）。
  3. LL 驱动大量函数是头内 static inline，不会进 .a，无法 FFI 链接——只封装 .c 中 public 非 inline 函数（如 LL_RCC_GetSystemClocksFreq、LL_GPIO_Init）。
  4. 绝不加带 main() 的示例 main.c，会和 cortex-m-rt 入口冲突。
- 验证：本机实际已具备 arm-none-eabi-gcc（Arm GNU Toolchain 15.2）与 thumbv7em-none-eabihf 目标；cargo build --target thumbv7em-none-eabihf 通过，nm 确认 .a 导出 LL_RCC_GetSystemClocksFreq/LL_GPIO_Init 等（标记 T）。最初误判缺工具链是 Bash env.sh 损坏（dirname 缺失）导致 command -v 误报。
- 注：本机 Bash 环境损坏——env.sh 报 dirname/cd/tail/grep/head 缺失，rm 也走坏掉 safe-bin 报错；cargo 仍可用，路径要用 Windows 风格（D:/...）而非 /d/...。

## py32e407cbind-rs 升级为 bindgen 自动生成（接上一条）

- 用户确认把手写 extern "C" 绑定升级为 bindgen 自动生成（参考 esp-idf-sys “raw 绑定 = bindgen + cc” 分层）。
- 改动：Cargo.toml [build-dependencies] 加 bindgen = "0.71"（实际锁 0.71.1）；新增 wrapper.h（只 include py32e407_ll_rcc.h / py32e407_ll_gpio.h）；build.rs 第 2 步用 bindgen::Builder 解析，use_core()+layout_tests(false) 适配 no_std，allowlist LL_RCC_.* / LL_GPIO_.* / ErrorStatus，clang_args 传 -target arm-none-eabi + -mcpu=cortex-m4 等 + -DPY32E407xE -DUSE_FULL_LL_DRIVER + 三处 include；src/lib.rs 改为 include!(concat!(env!("OUT_DIR"), "/bindings.rs"))，保留 LlRccClocks/LlGpioInit/GpioType 别名及 read()/zeroed() 便捷方法。
- 又踩 3 个坑（已解决）：
  1. build.rs 里误用 env!("OUT_DIR") 编译期宏 → 必须用 std::env::var("OUT_DIR")（OUT_DIR 只在运行时由 cargo 注入）。
  2. bindgen 的 <stdint.h> 路径：--print-sysroot 已返回 `.../arm-none-eabi`，newlib include 是 sysroot/include（不是再叠一层 arm-none-eabi）；叠错导致 cmsis_gcc.h 报 unknown type name 'uint32_t'。正确做法：用 arm-none-eabi-gcc --print-sysroot 拼 /include。
  3. 在 bindings.rs 顶部 raw_line("#![allow(...)]") 失败（inner attribute 不在文件最前，bindgen 已有 header 注释在前）；改在 lib.rs crate 顶层加 #![allow(non_snake_case, non_upper_case_globals, non_camel_case_types)]（include! 进来的绑定受其覆盖）。
- bindgen 保留原始 C 标识符（字段 Pin/Mode/Speed/OutputType/Pull/Alternate、SYSCLK_Frequency 等、宏 LL_RCC_HSE_4_8MHz），故 Rust 侧访问用 cfg.Pin 而非 cfg.pin。
- 验证：cargo build --target thumbv7em-none-eabihf 0 error 0 warning（仅 vendor 头自身 unused-parameter 的 C 警告）；nm 确认 libpy32e407_ll.a 导出 LL_RCC_DeInit/LL_RCC_GetSystemClocksFreq/LL_GPIO_DeInit/LL_GPIO_Init/LL_GPIO_StructInit 均为 T。FFI 链路打通。
- 扩展约定：以后加外设只需 build.rs 的 for src 列表 +1 个 .c、wrapper.h 加一行 #include、build.rs allowlist 加一条正则即可，无需再手写任何 extern/结构体。

## py32e407cbind-rs 全外设扩展 + 复查纠错（2026-09-13 深夜）

- 全外设接入：build.rs 改为**自动扫描** Src 全部 `py32e407_ll_*.c`（25 个），用 HAL_DEPENDENT
  排除依赖 HAL 的 usb/sdmmc → 实收 23 个；动态生成 `OUT_DIR/wrapper_gen.h` 含全部 LL 头
  （排除 usb/sdmmc.h）；allowlist 放宽为 `LL_.*` + `ErrorStatus`。构建 0 error（仅 vendor 的
  -Wunused-parameter C 警告）。新增外设无需再改 build.rs。
- **产物核对结论（正确）**：`.a` 全局 `T` 符号 **104** ↔ `bindings.rs` 的 `pub fn LL_` **104**，
  双向 0 误差（无悬空声明、无遗漏符号）；另含 **2432** 个 `pub const LL_` 常量与全部类型定义。
  即：bindgen 对「可外部链接的 LL API」是 100% 覆盖，流程与产物都对。
- ⚠️**重大测量陷阱（务必记住）**：PowerShell `Select-String` **默认大小写不敏感**！用它过滤 nm
  的 `" T LL_"` 会同时命中局部符号 `" t LL_"`，一度误判「.a 导出 294 个符号、bindgen 丢了 190
  个函数」。真相：`.a` 里 **221 个是 `static inline` 被实体化出的局部(`t`)副本**——头内 inline
  函数在 .c 里**只有调用、没有外部定义**（如 py32e407_ll_gpio.c 仅第 211 行调用
  LL_GPIO_SetPinMode），属内部链接，**本来就不可 FFI 链接**；bindgen 跳过它们完全正确。
  → 判符号可见性必须用 `Select-String -CaseSensitive` 或 `-cmatch`，区分大小写 T/t。
- 两次基于错误前提的改动**均已回滚**：(a) `generate_inline_functions(true)` 实测无效；
  (b) `-D__STATIC_INLINE=inline` **有害**——会为只有局部符号的函数生成 extern 声明，一调用就
  undefined reference。二者都不是“补全”，是引入链接失败。
- ℹ️ cargo 缓存陷阱：只删 `target/thumbv7em-none-eabihf` **不够**，build script 的编译产物与指纹
  在 `target/debug`（host 侧），build.rs 改动可能不重跑、复用旧 bindings.rs。强制重跑要删整个
  target，或临时加 `cargo:warning=哨兵` 确认脚本确实执行了。
- 遗留（非缺陷）：221 个头内 inline helper（LL_GPIO_SetPinMode/LL_TIM_SetPrescaler 等）无法经
  FFI 调用。若将来要暴露，正确途径是 `generate_inline_functions`（让 bindgen 把函数体翻成 Rust）
  或用 Rust 重写一层，而不是改成 extern 声明。
