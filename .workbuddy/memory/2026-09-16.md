### 关键结论（都已写进 esmc.rs 的 doc 注释）
1. **写 `ADDR24` 才是"开火"动作**：指令(INS1)与 24 位地址同处一个 32 位寄存器，
   配置阶段必须攒影子值一次整写，否则第一次写就会发起错误命令。HAL 用 `ContexAddr24`
   延迟到 `Transmit`/`Receive` 开头写——本驱动用句柄字段 `addr24` 复刻。
2. **HAL v0.7.0 笔误**：`ESMC_Config` 的 XIP 读/写分支各有一处
   `CLEAR_BIT(TmpXDCR, ESMC_XCR3_NO_ADDR)`（用 XCR3 掩码作用在 XDCR 上）。已按 RM 修正为
   清 `XCR3.NO_ADDR`，XDCR 只写 DUMMY/NO_CMD。
3. **Init 顺序按 RM 调整**：RM 30.4.2 要求模式 3 "先 CPOL/CPHA 再配 BAUD"，HAL 顺序相反。
4. **CR 整写 vs modify**：HAL `CR = SPIEN|2xQUAD` 会清掉 RM 记"复位值 1"的保留位 bit1，
   改用 `modify` 只动定义位。
5. **SVD/PAC 缺陷**：`XCR3`/`XCR3_WE` 缺 `NO_DATA`(bit7)；`IFR2.TXFIFOOVIF`(bit4, RC_W1)
   只有读侧无写入器（用整写位掩码清零）。
6. **BT 复用表列号规则**：DS `_ds.txt` 的 AF 行**只有 token 数 = 17 的行列号可信**
   （pin + 16 AF，`tokens[k] = AF(k-1)`）；残缺行必须例外程/引脚定义表交叉验证。
   实测 `PE15` 干净行给出 AF9=IO0 / AF10=IO3，与 PSRAM 例程 `GPIO_AF9_ESMC` 吻合。
7. **引脚硬证据**：官方 `Example/ESMC/*/Src/py32e407_hal_msp.c`——
   CLI/IO0/IO1/IO2/IO3/SS5 = PA3/PB1/PB0/PA7/PA6/PD2（全 AF10）；
   PSRAM 例程 = PE10/PE15/PE13/PE14/PE9/PE11（PE15 是 AF9，其余 AF10）。
   上拉：CLK/IO0/IO1=NoPull，IO2/IO3 与 nCS=PullUp，速度 VeryHigh。

### 关键新知识
1. **`参考设计/demo` 是 PY32Studio 生成的工程**（`Core/SRC/*.c`、`Core/INC/*.h`、
   `demo.pysprj`，另有 `build/Debug` 产物）：各外设 `HAL_*_MspInit` 直接给出
   `引脚 ------> 信号` + `GPIO_AFn_xxx`，**是"本板引脚/AF"最快最准的证据源**，
   以后查任何引脚的 AF 都先看这里，再考虑官方例程，最后才啃 DS 表。
2. 这条把 PB10 的 `ESMC_CLK` 从「AF9/AF10 二义」定成了 **AF10**：
   DS 表 3-4 的 PB10 行只有 16 个 token（丢了一格），同行标定（用已知 AF13 的
   `ETH_MII_RX_ER`）只能确认"丢了一格"，无法定位丢在哪，故二义；生成代码给答案。
3. **同一信号在不同引脚的 AF 列不统一**（实测 `FDCAN2_TX`：PB6=AF9、PB13=AF8；
   `USART3_TX`：PB9=AF6、PC10=AF7），所以残缺行不能拿别脚的 AF 去套。
4. **ESMC 的 XIP 映射窗口 = `0x0400_0000 – 0x07FF_FFFF`**（RM 表 3-5，64 MB）。
   16 MiB Flash 占 `0x0400_0000 – 0x04FF_FFFF`，**24 位地址正好够**，不用 32 位地址模式。
   RM 里另一处"ESMC 映射到 0x0000 0000"是**启动重映射**（从 ESMC 启动时才别名），别混淆。
5. PY32Studio 生成工程的 ESMC 默认档：`ClockPrescaler = 2`（SCLK = HCLK/2）、
   Mode0、单 Flash、`CS_HIGH 1 cycle / CS_HOLD 2 cycles`——与本驱动 `Config::default()` 对齐。
   生成代码对全部 ESMC 引脚用 `GPIO_NOPULL`，官方例程对 IO2/IO3/CS 用上拉；驱动取后者。
6. 环境：`Remove-Item` 会被 safe-delete 钩子拒（`trash-failed`），临时文件别乱撒在
   工程目录里，写到 `.workbuddy/` 下。

## 追加：ESMC 上板实测结果与三处修复（同日）

### 上板日志（用户实跑 `cargo run --release`）
```
ESMC ready: SCLK = 2000000 Hz, flash = 16 MiB (24-bit addr)
ESMC JEDEC ID = [0xc8, 0x60, 0x18]
ESMC status = [0x0]
ESMC flash[0..16] = [0xff ×16]
ESMC XIP setup failed: Invalid Configuration   ← 我的 bug
```
→ **间接读通路完全正确**（Mode0 / 2 MHz / 24 位地址 / 单线指令+地址）。

### 三处修复
1. **校验 bug**：`validate` 强制"有数据阶段就必须有 nb_data"，而 XIP 命令按定义不带
   nb_data（官方 XIP 例程也是 0）→ 必然误报 `InvalidConfig`。已拆分为
   `validate_common` / `validate_indirect`（要求 nb_data 与 data_mode 一致）/
   `validate_xip`（要求 nb_data == 0，data_mode 为 None 或与方向一致）。
2. **`0xEB` Dummy 由 6 改正为 4**：GD25 手册 §7.11「Quad I/O Fast Read (EBH)」明确
   是 3 字节地址 + Continuous Read Mode byte + **4 dummy clocks**（GD25Q128 与 GD25LQ128
   都一样）。原先按 W25Q 的 6 写会静默读出错位数据。**Dummy 是型号相关量，换料必查手册。**
3. **4 线读前必须置 QE 位**（SR2 bit1，读 `0x35` / 写 `0x31`，出厂为 0）：不置位则
   IO2/IO3 仍是 `#WP`/`#HOLD`，quad 读回垃圾。demo 里加了「读 SR2 → `|= 0x02` →
   `0x06` 写使能 → `0x31` 写回 → 等 BUSY 清零 → 回读确认」，与官方 polling 例程同序。
   注意这是**写 Flash 非易失状态位**。
4. 新增 `Esmc::xip_enabled()`；demo 在解引用 `0x0400_0000` 前先回读 `XIPEN` 确认
   （RM 30.3.4.2：XIPEN=0 时 XIP 总线被置忙，访问映射区可能挂住总线），
   读空片应得 `0xFFFFFFFF`。

### Flash 型号（重要）
`C8 60 18` = GigaDevice、容量 0x18 = 128 Mbit = **16 MiB** ✓（与用户所述一致）；
中段 `0x60` 按 flashrom `flashchips.h` 是 **GD25LQ128（LQ = 1.8V 档，1.65–2.0V）**，
而 `0x40` 才是 3.3V 的 GD25Q128。**已提示用户核对丝印与供电**：若确为 1.8V 器件，
3.3V 供电/驱动属超压（现在能读通，但长期不可靠）。JEDEC 三字节 = 厂商/类型/容量。

## 追加：第二轮上板 —— QE 未生效 + XIP 地址错误（同日）

### 上板日志要点
```
ESMC SR2 = 0x0, 置 QE 位…   →  ESMC SR2 回读 = 0x0      ← QE 没写进去
ESMC XIP on: ... XIPEN=true
HardFault <Escalated BusFault <Precise data access error at location: 0x04000000>>
```

### 结论 1：XIP 窗口地址我搞错了 —— 是 **0x9000_0000**，不是 0x0400_0000
- RM **表 3-1「存储器地址」**：`0x9000_0000` = **ESMC Bank1**（寄存器块在 0xA000_1000）；
  厂商 `ESMC_MemoryMapping_QSPI` 里 `ApplicationAddress = 0x90000000` ✓
- `0x0400_0000–0x07FF_FFFF` 只是 RM **表 3-5「物理重映射地址」**的**启动重映射视图**
  （配 `HAL_SYSCFG_SetRemapMemory(SYSCFG_BOOT_ESMC)`、从地址 0 读，用于 IAP 跳转）。
  正常 Flash 启动时表 3-1 写明 `0x0008_0000–0x07FF_FFFF` 是**保留区**，
  "CPU 读写该空间产生 Response error → HardFault" —— 与实测的精确 BusFault 完全对上。
- **教训**：RM 里"重映射/别名"表（表 3-5）与"真实地址映射"表（表 3-1）必须分清。

### 结论 2：XIP 配置改用厂商例程那一套
`0x6B`（1-1-4 Quad Output）+ 单线地址 + **无备用字节** + **8 Dummy**（0x6B 的 Dummy
跨 W25Q/GD25/P25Q 恒为 8）。`0xEB` 需要模式字节 `M=0x00` + 4 线地址 + Dummy=4。

### 结论 3：QE 没写进去，已加三段式排查链（待下一轮结果）
WEL 是唯一抓手：① WREN 后读 SR1 看 WEL 是否置位 → 验证 **SFCR 指令通路**；
② 写 SR 命令后 WEL 是否自动清零 → 验证**间接写数据通路**；③ 再看回读值。
另加 `0x01`(写 SR1+SR2 两字节) 作 `0x31` 的备选。demo 还会跑「单线 XIP(0x03)」与
「4 线 XIP(0x6B)」各一次做对比：都对 = 一切正常；只有单线对 = QE/Dummy 不对。

### 其它
- 上板耗时提醒：demo 里那次 `read_volatile` 直接把程序打挂了（HardFault 无 handler），
  所以**解引用映射地址前必须先读回 XIPEN 确认**，并且选对地址。

## 追加：第三轮上板 —— ESMC 全链路跑通（同日）

### 最终结果（全部 OK）
```
ESMC JEDEC ID = [0xc8, 0x60, 0x18]      ESMC SR1 = 0x0    ESMC SR2 = 0x2 (QE 已置)
ESMC 擦写自检 1B:  [0xa5] → OK            ESMC 擦写自检 13B: [0x0..0xc] → OK
ESMC XIP(0x03 单线) @0x90fff010 = 0x3020100
ESMC XIP(0x6B 4线)  @0x90fff010 = 0x3020100   → 单线 OK / 4线 OK
```
即：间接读写（含 4KB 擦除、页编程）、单线 XIP、**4 线 XIP 全部验证通过**。

### 根因：GD25LQ128 的指令表里没有 `31H`
- GD25LQ128 手册 Table 2：写状态寄存器**只有 `01H | S7-S0 | S15-S8`**；读侧
  `05H`(S7-S0)/`35H`(S15-S8)/`15H`(S1-S0)。**没有 31H**。
- 手册 7.4 两条硬约束：数据阶段只能 8 或 16 bit（否则整条命令不执行）；
  **只发 8 bit 会把 QE 清零** → 置 QE 必须发满 2 字节。
- 厂商 STK 例程的 `0x31` 只对 **P25Q64** 成立（我们照抄了别的型号的例程）。
- 实测佐证：`0x31` → WEL 不消失、SR2 不变；`0x01` 2 字节 → WEL 清零、SR2=0x02。
  **WEL 只在写类命令真正执行后复位，读状态不会清它**，所以它是"命令有没有执行"的唯一抓手。
- 同批证明 **1 字节 TX 数据阶段可用**（页编程 1 字节读回一致）→ `0x31` 失败与字节写入无关。

### 方法论修正：空片的 0xFF 没有判别力
之前两轮"读出 0xFFFFFFFF"其实什么都没证明 —— QE 没置、Dummy 错、数据线断都会得到 0xFF。
改成**草稿扇区（末 4KB `0x00FF_F000`）擦除 → 写非 0xFF 图案 → 读回比对 → 同址单线/4线
XIP 对比**，一次就同时验证了写通路与 4 线读。**"这个结果在什么情况下会不同"应作为写测试
前的自问。**

### 关键结论（已写入代码注释 + 技能 `references/hardware-flow.md`）
1. **EXTI 无时钟门控**：`py32e407_ll_bus.h` 里只有 `LL_APB2_GRP1_PERIPH_SYSCFG` 没有 `EXTIEN`；
   只有 SYSCFG 要 `APB2ENR.bit0`（`rcc::init` 已置）。
2. **端口选择在 SYSCFG 不在 EXTI**：`SYS_EXTICR1–4` @0x14/0x18/0x1C/0x20，每线 4-bit 半字节、
   偏移 `(line%4)*4`，编码 0=PA…5=PF（与 `Pin::port()` 一致）。写前必须开 SYSCFG 时钟。
3. **寄存器分组**：`IMR1/EMR1`=0–31、`IMR2/EMR2`=32–34（只用 bit0–2）、
   **`RTSR/FTSR/SWIER/PR` 只覆盖 0–21**（无 `PR2`/`RTSR2`）。复位值 `IMR1=0xC3C0_0000`、
   `IMR2=0x7`（都是唤醒线，必须只动目标位、别整写）。
4. **向量表不是 STM32F4 那套**：`EXTI0`=6/`EXTI1`=7/`EXTI2`=8/`EXTI3`=9/`EXTI4`=10/
   `EXTI9_5`=23/`EXTI15_10`=40（RM 13.1.3）；没有 `EXTI0_1`/`EXTI2_3`/`EXTI4_15`。
5. **`IMR` 与 `PR` 无关**：边沿置起 `PR` 由硬件完成，`IMR` 只管要不要发 NVIC 请求；
   所以"只开 IMR + 轮询 PR"合法，但开了 EXTI 就必须及时清 `PR`。
6. **PAC 坑（这轮踩到）**：svd2rust 0.37 的 `Reg::modify()`/`write()` 返回 `REG::Ux`(u32)，
   **尾表达式位置**的 `match` 会报 `expected (), found u32`，补 `;` 即可。
7. `PR` 的 RC_W1 在 SVD 里没标 `oneToClear` → 只生成 `BitWriter`，清挂起必须整写 `w.bits(1<<line)`。
8. **本板 EXTI 引脚 = PD10**：`参考设计/demo/Core/SRC/gpio.c` 配 `GPIO_MODE_IT_RISING` +
   `GPIO_NOPULL`，对应 `EXTI15_10_IRQHandler` → `HAL_GPIO_EXTI_IRQHandler(GPIO_PIN_10)`
   （`py32e407_it.c`）。demo 照抄该引脚/触发沿。
9. **`HAL_GPIO_Init` 的 EXTI 段是 GPIO+EXTI 的权威顺序**（比 `HAL_EXTI_SetConfigLine` 更实用）：
   SYSCFG 时钟 → EXTICR → IMR1 → EMR1 → RTSR → FTSR；**HAL 不清 `PR`**，本驱动补清一次
   （embassy-stm32 也清），避免配置残留挂起位导致 IMR 一开就伪中断。

`references/style-guide.md` 记入 `modify()/write()` 返回值坑、`SKILL.md` 的

## 修正：EXTI 驱动按 embassy-stm32 的 API 面重写（同日，用户要求）

### 触发点
用户指出"要按照 embassy-stm32 的格式"。第一版按 HAL 的 `HAL_EXTI_*` 自作主张加了
**embassy-stm32 里不存在的公开项**：`ExtiLine`、`exti::Error`、`Mode`、
`generate_sw_interrupt`、`enable_event`/`disable_event`、`into_input`、`ExtiInput::line()`、
`line` 常量模块——属自创 API，**违反"API 形态严格对齐 embassy-stm32"这条项目硬约束**。

### 重写后的形态（逐项照搬 embassy-stm32 的文件划分与命名）
- `src/exti/mod.rs`：`ExtiInput<'d>` + `Channel` + `impl_exti!` + 电平读取 +
  `new_blocking` / `set_edge_detection` / `enable_interrupt` / `disable_interrupt` /
  `clear_pending` / `is_pending` / 私有 `pin_mask`
- `src/exti/low_level.rs`：`TriggerEdge` / `InterruptState` / `configure_exti_pin` /
  `set_exti_interrupt_enabled` / `clear_exti_pending_mask` / `clear_exti_pending` /
  `is_exti_pending`（全部 `pub(super)`，只接受 GPIO 线 0–15）
- `src/exti/blocking.rs`：**新增** `ExtiGroupMask`（`new(&[&ExtiInput])` + `clear()`）
- 模块 doc 里加了一张「相对 embassy-stm32 的同步裁剪」表，逐条说明未实现项的去向

### 两处必要的工程适配（已在 doc 中注明）
1. `Channel::number()` 同名，但省掉 `irq()` / `type IRQ`（依赖 `crate::interrupt::typelevel`，
   本库尚无中断类型层）→ 中断向量由用户自己实现。
2. `ExtiInput` 无 `Mode` 泛型（纯同步库，与 `uart`/`i2c`/`timer`/`esmc`/`gpio` 一致），
   即 `ExtiInput<'d>` ≡ embassy-stm32 的 `ExtiInput<'d, Blocking>`；Async 面
   （`wait_for_*`、`from_input`/`from_flex`、`ExtiInputFuture`、`EXTI_WAKERS`）整体推迟。
   为此在 `gpio.rs` 加了 `pub(crate) fn Input::pin()/port()`、把 `Flex::port_pin`
   放开为 `pub(crate)`——`new_blocking` 需从 `Input` 读回引脚号/端口号
   （embassy-stm32 靠 `pin.pin.pin.pin()`，我们的字段对外私有）。

### demo 侧
`exti_demo` 不再调自创的 `generate_sw_interrupt`：自检改为**直接点 PAC 的 `SWIER`**
造一次挂起，再走 `is_pending()` → `clear_pending()` → `is_pending()`，
仍有判别力且不扩大 HAL 面（与该文件里 TIM7 中断写 PAC 的风格一致）。
